# ADR-0003: 콘텐츠 원본은 이력서·포트폴리오 같은 원본 파일이고, 허용 목록으로 동기화한다

- 상태: 채택 (동기화 스크립트는 1차에서 구현, 구현 원칙과 원본에 없는 작업 2026-10-14 추가, Recueve는 2026-10-15 원본에 들어와 원본에 없는 작업에서 뺌, 첫 화면 기술 층의 짝은 2026-10-16부터 ADR-0010, AI 도구 활용 사례 원본 2026-10-20 추가, 원본에 있는 작업의 본인 확인 사실 2026-10-23 추가)
- 날짜: 2026-10-14

## 배경

이력서와 포트폴리오는 이미 md 원본에서 PDF를 만들어 쓰고 있습니다. 홈페이지에 같은 내용을 다시 쓰면 세 벌이 생기고, 수치나 날짜가 하나씩 어긋나기 시작합니다.

원본이 있는 커리어 저장소는 비공개입니다. 공개하면 안 되는 개인 문서도 함께 들어 있습니다.

## 검토한 안

| 안 | 장점 | 단점 |
|---|---|---|
| 홈페이지를 커리어 저장소 안에 둔다 | 원본을 바로 읽는다 | 저장소를 공개할 수 없다. 배포 서비스가 비공개 문서 전체에 접근한다 |
| 사이트용 글을 따로 쓴다 | 단순하다 | 내용이 세 벌이 되어 어긋난다 |
| 별도 저장소 + 허용 목록 동기화 | 원본은 하나, 저장소는 공개 가능 | 동기화 스크립트가 필요하다 |

## 결정

- 홈페이지는 별도 공개 저장소로 둡니다.
- `npm run sync`가 커리어 저장소에서 **허용 목록에 있는 파일만** 가져와 `content/synced/`에 씁니다. 허용 목록 밖의 파일은 읽지 않습니다.
- 가져올 때 연락처 표에서 전화번호를 지웁니다. 그 뒤 민감정보 검사를 한 번 더 돌립니다.
- 원본 저장소 경로는 환경변수 `CAREER_DIR`(`.env.local`, git 제외)로 받습니다. 코드에 경로를 적지 않습니다.
- `content/synced/`는 커밋합니다. 원본 저장소가 없어도 누구나 빌드할 수 있고, 배포 서비스는 공개 저장소만 봅니다.
- 사이트에서만 쓰는 글(한 줄 소개, AI 작업 카드, 원본에 없는 작업 소개)은 `content/site/`에 직접 씁니다.

## 구현 원칙

동기화 스크립트를 만들기 전에 정했습니다(2026-10-14).

### 공개 범위가 다른 내용

- 이 저장소 작업 때문에 원본을 고치지 않습니다. 공개 페이지에 맞게 빼거나 고칠 내용은 모두 동기화 규칙으로 처리합니다. 원본 문서에만 맞는 문구도, 틀렸거나 근거가 약한 내용도 같습니다.
- 원본에도 반영할 만한 수정은 원본 저장소의 `docs/todo/`에 남깁니다. 원본에 반영할지는 그쪽에서 정합니다.
- 동기화 규칙은 공개 저장소에 들어가므로 값이 아니라 항목 이름으로 찾습니다. 찾던 대상이 원본에 없으면 동기화를 멈춥니다. 원본에 수정이 반영되면 이렇게 멈추므로, 그때 해당 규칙을 지웁니다.
- 원본에서 빠졌지만 사이트에는 남길 절도 동기화 규칙으로 덧붙입니다. 원본에 같은 제목의 절이 다시 생기면 동기화를 멈추므로, 그때 규칙을 지웁니다. 원본 이력서가 자격증 절을 뺐을 때 사이트의 이력서에는 남기기로 하면서 더했습니다(2026-10-27).
- 전화번호는 연락처 표에서 머리글이 `전화번호`인 열을 통째로 지웁니다.
- 허용 목록과 변환 규칙은 `scripts/sync.config.mjs` 한 파일에 둡니다. 무엇을 공개하는지가 이 파일의 diff로 보입니다.

### 쓰기 전에 막기

- 변환 결과를 파일에 쓰기 전에 민감정보 규칙과 비공개 금지어로 검사합니다. 한 건이라도 걸리면 아무 파일도 쓰지 않습니다. 검사 규칙은 `check:sensitive`와 같은 모듈을 씁니다.
- 비공개 금지어 목록(`.sensitive-terms.local`)이 없으면 실행하지 않습니다. 빈 파일은 일부러 비운 것으로 보고 허용합니다.
- 허용 목록의 파일이 없거나 링크로 원본 저장소 밖을 가리키면 건너뛰지 않고 멈춥니다.
- 오류 메시지에는 원본 내용을 그대로 찍지 않습니다.

### 원본과 결과의 대응

- 원본 저장소에 커밋하지 않은 변경이 있으면 실행하지 않습니다. 미리 보기용 `--allow-dirty`로 실행하면 그 사실이 manifest에 남습니다.
- manifest(`content/synced/manifest.json`)에는 원본 커밋 해시, 커밋 안 된 변경 여부, 출력 파일 목록, 적용한 변환만 적습니다. 원본 파일의 해시와 경로는 적지 않습니다. 결과와 원본은 지운 값만 다르므로, 원본 해시가 공개되면 지운 값을 하나씩 대입해 맞춰 볼 수 있기 때문입니다. 전화번호는 경우의 수가 1억 개뿐이라 몇 초면 됩니다.
- `content/synced/`는 동기화 스크립트가 전부 맡습니다. 매번 비우고 다시 써서 허용 목록에서 뺀 파일이 남지 않게 합니다.
- `npm run sync -- --check`는 파일을 쓰지 않고 `content/synced/`가 원본에서 다시 만든 결과와 같은지만 확인합니다.

### 원본에 없는 작업

사이트에서 소개하는 작업 중 이력서와 포트폴리오에 없는 것은 `content/site/`에 사이트 전용 글로 씁니다.

| 작업 | 글 |
|---|---|
| Brain House, AI TOOLS | `content/site/sites/` |
| Jake Wiki, 영상 제작, Jake Hermes, 작업 환경 | `content/site/ai/` |

- 이 글에는 공개된 곳(라이브 사이트, 공개 저장소, 공개 영상)에서 확인할 수 있는 사실과 제가 확인한 사실(기간, 역할, 스택, 만든 방법)만 넣습니다.
- 공개하지 않는 자료(개인 위키의 내용 등)는 방법만 쓰고, 내용과 화면은 싣지 않습니다.
- 원본에 같은 내용이 없으므로 여러 벌이 어긋나는 문제는 생기지 않습니다.

### 판단

AI는 독자에 따라 다른 내용만 동기화 규칙으로 빼고, 틀렸거나 근거가 약한 내용은 원본에서 고치자고 제안했습니다. 원본을 하나로 두자는 취지였습니다. 저는 원본은 고치지 않고 사이트에 맞는 내용을 따로 쓰기로 했습니다. 사이트에 맞게 고친 내용은 원본 저장소의 할 일로 넘겨, 원본에 반영할지는 그쪽에서 따로 정합니다.

## 원본 추가: AI 도구 활용 사례 (2026-10-20)

### 배경

`/ai/case`에 AI 도구 활용 사례(4컷과 본문)를 싣기로 했습니다. 이 사례는 커리어 저장소에서 PDF로 만드는 문서이고, PDF는 `AI활용사례/`의 세 파일로 만듭니다.

| 파일 | 담은 것 |
|---|---|
| `ProWith.txt` | 본문 문단 |
| `ProWith.json` | 제목, 부제, 4컷 설명, 그림에서 칸마다 자를 자리, 본문 제목 |
| `ProWith-4컷.png` | 4컷 그림 한 장(1024×1024) |

본문에는 포트폴리오에 없는 사실(가이드 문서 수, 표 규칙을 다른 서비스에 가져다 쓴 일)이 있습니다. 이 결정 전에는 포트폴리오에 없는 사실을 사이트에 쓸 수 없었습니다.

### 검토한 안

| 안 | 장점 | 단점 |
|---|---|---|
| 본문을 사이트 전용 글(`content/site/`)로 옮긴다 | 동기화를 고치지 않는다 | 같은 글이 두 벌이 된다. 새 사실을 포트폴리오에도 넣어야 대조할 수 있다 |
| PDF를 원본으로 읽는다 | 파일이 하나다 | 글자를 뽑으면 줄과 순서가 깨지고, 그림은 PDF 안에서 다시 잘라야 한다. PDF를 읽는 라이브러리가 더 필요하다. 본문을 고친 뒤 PDF를 다시 만들어야 사이트에 반영된다 |
| 세 파일을 허용 목록에 더한다 | 원본이 하나이고, PDF와 사이트가 같은 파일에서 나온다 | 동기화가 그림 파일을 다뤄야 한다 |

### 판단

AI는 처음에 본문을 사이트 전용 글로 옮기고 사실은 포트폴리오와 대조하자고 제안했습니다. 저는 동기화 대상을 확인한 뒤 사례 파일을 원본 저장소의 `AI활용사례/`로 옮겼고, PDF를 원본으로 쓸 수 있는지 물었습니다. AI는 PDF가 세 파일로 만든 결과물이라는 점을 들어, 이력서와 포트폴리오처럼 결과물이 아니라 그것을 만드는 파일을 읽자고 했습니다. 저는 그 제안을 받아들였습니다.

### 결정

- `AI활용사례/`의 세 파일을 허용 목록에 더합니다. 이 ADR의 원본은 형식(md)이 아니라 "PDF 같은 결과물을 만드는 파일"을 뜻하도록 제목을 넓힙니다.
- 부제의 작성자 이름(`| 소재희`)은 동기화 규칙으로 뺍니다. 이름은 사이트 머리와 푸터에 이미 있습니다.
- 그림 파일도 동기화로 가져옵니다. 동기화가 글이 아닌 파일을 다루는 첫 경우입니다.
  - 민감정보 검사는 글자만 읽으므로, 그림은 가져올 때 눈으로 확인합니다. 포트폴리오 이미지를 싣지 않기로 한 것과 같은 기준입니다(02-ia.md `/work`의 이미지).
  - `npm run sync -- --check`는 그림도 원본과 같은지 비교합니다.
- 4컷을 칸마다 자르는 일은 동기화가 아니라 사이트가 합니다. 원본 그림과 자를 자리를 그대로 가져오고, 사이트에 맞춘 처리(가장자리 여백 빼기)는 이 저장소의 코드에 둡니다.

## 원본에 있는 작업의 본인 확인 사실 (2026-10-23)

### 배경

홈 서비스 섹션 제목에 세 서비스를 혼자 만들었다는 것을 쓰기로 했습니다. 포트폴리오에서 "혼자"라는 말은 Recueve 상세("기획·디자인·개발·인프라·운영을 혼자 맡아 공개한 서비스입니다.")에만 있습니다. ProWith는 "프리랜서 프로젝트", GENYS Lotto AI는 "개인 프로젝트"로만 적혀 있습니다.

같은 날 운영 화면에서 제목을 본 뒤 제목은 "운영 중인 서비스"로 되돌리고, 혼자 만들었다는 것은 섹션 소개 문장으로 옮겼습니다. 아래 기준은 그대로 둡니다.

### 판단

AI는 사이트에 쓰기 전에 원본 포트폴리오에도 같은 말을 넣자고 제안했습니다. 원본에 있는 사실만 쓴다는 이 ADR의 기준을 문장 단위로 적용한 것입니다. 저는 원본에 같은 문장이 없다고 사실이 아닌 것은 아니고, 원본과 어긋나지도 않는다고 판단했습니다. 원본 첫머리에도 "기획부터 개발, 배포까지 혼자서도 끝까지 해냅니다."가 있습니다. 세 서비스를 모두 같은 말로 적어 둘 필요도 없습니다.

### 결정

- 원본에 있는 작업이라도, 제 작업에 대해 제가 확인한 사실(역할, 혼자 했는지, 만든 방법)은 원본에 같은 문장이 없어도 사이트 글에 씁니다. 원본에 없는 작업의 사이트 전용 글과 같은 기준입니다.
- 원본과 어긋나는 사실은 쓰지 않습니다. 수치, 날짜, 회사명, 기술명은 지금처럼 원본에서만 가져옵니다(첫 화면 기술 층은 ADR-0010).
- 쓴 곳의 주석에 제가 확인한 사실이라는 것과 날짜를 남깁니다.

## 영향

- 이력서·포트폴리오에서 온 내용을 사이트에서 바꿀 때는 동기화 규칙을 더합니다. 원본과 `content/synced/`는 직접 고치지 않습니다.
- 동기화 결과의 변경분이 커밋 diff로 보이므로, 무엇이 공개되는지 커밋할 때마다 확인할 수 있습니다.
