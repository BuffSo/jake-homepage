# ADR-0010: 첫 화면 기술 층의 기술-서비스 짝은 각 서비스의 소스 코드로 확인한다

- 상태: 채택
- 날짜: 2026-10-16

## 배경

첫 화면의 기술 층은 층을 누르면 서비스마다 그 층에서 쓴 기술을 보여 줍니다. 지금까지는 그 짝을 이력서·포트폴리오의 서비스 항목에 나오는 낱말로 정했습니다(ADR-0003). 원문에 이름은 없어도 원문에서 따라 나오는 짝은 근거 낱말로 적었습니다.

그런데 이력서와 포트폴리오는 서비스마다 대표 기술만 적습니다. 그래서 실제로 쓴 기술이 층에서 빠졌습니다.

- ProWith와 GENYS Lotto AI도 Tailwind를 쓰는데 Recueve에만 표시됐습니다.
- ProWith에는 API 서버 안에서 도는 예약 작업이 있는데 워커 층에서 흐려졌습니다.
- GENYS Lotto AI도 Claude Code로 개발했는데 AI 층에서 흐려졌습니다.

## 검토한 안

| 안 | 장점 | 단점 |
|---|---|---|
| 지금처럼 원문 낱말로 정한다 | CI에서 모두 확인된다 | 원문이 대표 기술만 적어 실제와 어긋난다 |
| 원본 이력서에 기술을 더 적는다 | 근거가 한 곳이다 | 지원 서류용 원본을 홈페이지 때문에 고치게 된다 |
| 각 서비스의 소스 코드를 근거로 한다 | 실제로 쓴 기술이 그대로 나온다 | 서비스 저장소가 비공개라 CI에서 읽을 수 없다 |

## 판단

AI는 처음에 원문 낱말만으로 짝을 정하고, 빠진 기술은 원본에 먼저 넣자고 제안했습니다. 저는 이력서가 대표 기술만 적는 문서라고 보고, 정확하게 보여 주려면 코드를 봐야 한다고 판단했습니다. 원본은 그대로 둡니다.

## 결정

- ADR-0003의 예외로, **기술 층에 싣는 기술 이름과 기술-서비스 짝만** 각 서비스의 소스 코드를 근거로 합니다. 그래서 층에는 원문에 없는 기술 이름(shadcn/ui 등)도 코드에 표지가 있으면 실을 수 있습니다. 그 밖의 사실(수치, 기간, 소개 문장)은 계속 이력서·포트폴리오가 근거입니다.
- 기술마다 코드에서 찾을 표지를 `scripts/stack.config.mjs`에 둡니다. 표지는 의존성 이름, 파일 이름, 특정 파일 안의 낱말입니다.
  - 이 파일은 공개 저장소에 들어갑니다. 그래서 패키지와 파일 이름만 적고, 저장소 경로와 코드는 적지 않습니다.
- `npm run check:stack`이 세 서비스 폴더에서 표지를 찾습니다.
  - 찾은 결과가 `content/site/home.md`의 `usedBy`와 정확히 같아야 통과합니다(양방향).
  - 폴더 경로는 `.env.local`(git 제외)의 `RECUEVE_DIR`, `PROWITH_DIR`, `LOTTO_DIR`로 받습니다.
  - 폴더가 없는 곳(CI)에서는 건너뜁니다.
- CI 테스트(`npm test`)는 두 가지를 봅니다.
  - 서비스 항목(이력서·포트폴리오)에 이름이 나오는 기술은 그 서비스에 반드시 표시됩니다(한 방향).
  - 층의 기술 이름과 표지 설정의 기술 이름이 같습니다.
- 원문에서 따라 나오는 짝을 적던 근거 낱말(`evidence`)은 없앱니다. 코드가 직접 근거가 되기 때문입니다.

## 영향

- 서비스 코드가 바뀌면(기술을 더하거나 빼면) `npm run check:stack`이 어긋남을 알려 줍니다. 층 데이터는 그때 고칩니다.
- 표지는 코드의 흔적이라 완벽하지 않습니다. 예를 들어 Vercel은 배포 설정 폴더나 README의 언급으로, Gemini는 이미지 생성 도구가 남긴 파일로 확인합니다. 표지마다 무엇을 근거로 삼는지 설정 파일 주석에 적습니다.
- CI는 서비스 코드를 볼 수 없으므로, 층 데이터를 고친 PR에서는 로컬에서 `npm run check:stack`을 돌린 결과를 테스트 체크리스트에 적습니다.
